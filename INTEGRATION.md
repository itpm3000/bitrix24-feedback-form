# Интеграция кастомной формы обратной связи с Bitrix24 (воронка HelpDesk)

Спецификация REST-запросов, безотносительно языка программирования. По ней бэкенд может
реализовать приём собственной формы и создание в CRM **Контакта + Сделки** (сделка
привязана к контакту) в воронке **HelpDesk**.

> Запросы к порталу должны идти **с сервера** (бэкенд-прокси), а не из браузера:
> URL вебхука — это секрет, его нельзя светить в клиентском коде. Форма на сайте шлёт
> данные на ваш бэкенд, бэкенд обращается к Bitrix24.

---

## 1. Авторизация и формат вызова

Используется **входящий вебхук** Bitrix24 с правом (scope) **`crm`**.

```
BASE = https://<portal>.bitrix24.ru/rest/<user_id>/<webhook_token>/
```

- Любой метод вызывается как `POST {BASE}<method>.json`
- Заголовок: `Content-Type: application/json`
- Тело запроса: JSON-объект с параметрами метода
- Обязательно указывать непустой заголовок **`User-Agent`** (портал режет запросы с пустым UA)
- Ответ: JSON. Успех — поле `result`; ошибка — поля `error` и `error_description`

---

## 2. Общая логика

```
1. Поиск дубля контакта по email и телефону.
2a. Контакт найден  → создать только сделку с CONTACT_ID найденного контакта.
2b. Контакт не найден → создать контакт, затем сделку с CONTACT_ID нового контакта.
```

Ниже два эквивалентных способа. **Подход A** проще для реализации (обычные последовательные
вызовы). **Подход B** — оптимизация через `batch` (меньше запросов, важно на больших объёмах).

---

## 3. Подход A — последовательные вызовы (рекомендуется)

### Шаг 1. Поиск дубля контакта

Вызвать по каждому заполненному каналу связи. Метод: `crm.duplicate.findbycomm`.

**POST** `{BASE}crm.duplicate.findbycomm.json`
```json
{ "entity_type": "CONTACT", "type": "EMAIL", "values": ["ivan@example.com"] }
```
и/или
```json
{ "entity_type": "CONTACT", "type": "PHONE", "values": ["+79001234567"] }
```

Ответ (если найден контакт):
```json
{ "result": { "CONTACT": [16] } }
```
Берём первый ID из `result.CONTACT`. Если массив пуст/отсутствует — дубля нет.

### Шаг 2. Создание контакта (только если дубль не найден)

**POST** `{BASE}crm.contact.add.json`
```json
{
  "fields": {
    "NAME": "Иван",
    "LAST_NAME": "Петров",
    "OPENED": "Y",
    "TYPE_ID": "CLIENT",
    "SOURCE_ID": "WEB",
    "EMAIL": [ { "VALUE": "ivan@example.com", "VALUE_TYPE": "WORK" } ],
    "PHONE": [ { "VALUE": "+79001234567", "VALUE_TYPE": "WORK" } ],
    "IM": [ { "VALUE": "@ivan_petrov", "VALUE_TYPE": "TELEGRAM" } ],
    "UF_CRM_1786546554": "user-42"
  }
}
```
Ответ: `{ "result": 123 }` — ID нового контакта.

> `EMAIL` и `PHONE` — **множественные** поля: массив объектов `{VALUE, VALUE_TYPE}`,
> а не строка. `VALUE_TYPE`: `WORK` | `MOBILE` | `HOME` | `OTHER`.

### Шаг 3. Создание сделки

**POST** `{BASE}crm.deal.add.json`
```json
{
  "fields": {
    "TITLE": "Обращение с сайта site-a.com — Иван Петров",
    "CATEGORY_ID": 2,
    "STAGE_ID": "C2:NEW",
    "CONTACT_ID": 123,
    "SOURCE_ID": "WEB",
    "SOURCE_DESCRIPTION": "site-a.com | https://site-a.com/contacts",
    "COMMENTS": "Текст обращения + сводка по источнику",
    "UF_CRM_1786700225371": "Не проходит платёж по QR",
    "UF_CRM_1786685648580": 188,
    "UF_CRM_1786685952807": 158,
    "UTM_SOURCE": "google",
    "UTM_MEDIUM": "cpc",
    "UTM_CAMPAIGN": "helpdesk"
  }
}
```
Ответ: `{ "result": 4567 }` — ID новой сделки. `CONTACT_ID` связывает сделку с контактом.

> Если контакт был найден на Шаге 1 — Шаг 2 пропускается, а в Шаг 3 подставляется
> найденный ID. Дубли контактов не создаются.

## 4. Подход B — batch (одним/двумя запросами)

Метод `batch` выполняет до 50 команд за один HTTP-запрос и умеет подставлять результат
предыдущей команды в следующую через `$result[<ключ>]`.

> ⚠️ **Важно:** сырой endpoint `batch` принимает команды **строками вида**
> `"<method>?<url-encoded-параметры>"`. Форма `{ "method": ..., "params": ... }`
> сырым endpoint **игнорируется** (вернётся пустой результат). Клиентские библиотеки
> (`CRest::callBatch`, `BX24.callBatch`) принимают объекты и сами конвертируют в строки.

**Создание контакта + сделки одним пакетом** (когда дубль не найден):

**POST** `{BASE}batch.json`
```json
{
  "halt": 1,
  "cmd": {
    "contact": "crm.contact.add?fields[NAME]=Иван&fields[LAST_NAME]=Петров&fields[EMAIL][0][VALUE]=ivan%40example.com&fields[EMAIL][0][VALUE_TYPE]=WORK",
    "deal": "crm.deal.add?fields[TITLE]=Обращение&fields[CATEGORY_ID]=2&fields[STAGE_ID]=C2:NEW&fields[CONTACT_ID]=$result[contact]"
  }
}
```
- `halt: 1` — остановить пакет при первой ошибке.
- `fields[CONTACT_ID]=$result[contact]` — подставится ID контакта, созданного командой `contact`.
- Ответ: `result.result.contact` = ID контакта, `result.result.deal` = ID сделки;
  ошибки по командам — в `result.result_error.<ключ>`.

> **batch НЕ транзакционный.** Если контакт создан, а сделка упала — контакт **не откатывается**
> автоматически. Чтобы не плодить «висячие» контакты: проверить ответ и, если
> `result.result.contact` есть, а `result.result.deal` нет — удалить контакт:
> **POST** `{BASE}crm.contact.delete.json` c телом `{ "id": <contactId> }`.

Проверку дублей тоже можно упаковать в batch (2 команды `crm.duplicate.findbycomm`), но
проще выполнить её отдельными вызовами из Подхода A.

## 5. Справочник полей

### Фиксированные значения (воронка HelpDesk)

| Поле сделки | Значение | Смысл |
|---|---|---|
| `CATEGORY_ID` | `2` | воронка HelpDesk |
| `STAGE_ID` | `C2:NEW` | стартовая стадия «Новая» |
| `SOURCE_ID` | `WEB` | источник «Веб-сайт» |

### Поля контакта

| Поле | Тип | Назначение |
|---|---|---|
| `NAME` | строка | имя |
| `LAST_NAME` | строка | фамилия |
| `SECOND_NAME` | строка | отчество |
| `EMAIL` | множественное `[{VALUE,VALUE_TYPE}]` | email |
| `PHONE` | множественное `[{VALUE,VALUE_TYPE}]` | телефон |
| `IM` | множественное `[{VALUE,VALUE_TYPE}]` | мессенджер (Telegram и др.) |
| `UF_CRM_1786546554` | строка | ID пользователя на сайте обращения |

> Отдельного поля под Telegram нет — аккаунт пишется в штатное мультиполе `IM`
> с `VALUE_TYPE: "TELEGRAM"`. Другие типы: `SKYPE`, `VIBER`, `FACEBOOK`, `VK`, `INSTAGRAM`.
> Пример: `"IM": [ { "VALUE": "@ivan_petrov", "VALUE_TYPE": "TELEGRAM" } ]`

### Поля сделки HelpDesk (пользовательские)

| Код | Тип | Назначение |
|---|---|---|
| `UF_CRM_1786700225371` | строка | Описание проблемы |
| `UF_CRM_1786685648580` | список | Категория обращения (см. ниже) |
| `UF_CRM_1786685952807` | список | Приоритет (см. ниже) |
| `UF_CRM_1786686105228` | список | Способ оплаты (см. ниже) |
| `UF_CRM_1786686034932` | строка | Client/User ID |
| `UF_CRM_1786686054889` | строка | Order ID |
| `UF_CRM_1786686076193` | строка | Transaction ID |

Стандартные текстовые поля сделки: `TITLE`, `COMMENTS`, `SOURCE_DESCRIPTION`,
UTM — `UTM_SOURCE`, `UTM_MEDIUM`, `UTM_CAMPAIGN`, `UTM_CONTENT`, `UTM_TERM`.

### Значения списков (передавать числовой ID)

**Категория `UF_CRM_1786685648580`:**

| ID | Значение |
|---|---|
| 150 | Платеж |
| 152 | KYC / Верификация |
| 184 | AML / Комплаенс |
| 186 | Мошенничество / Риск |
| 188 | Техническая проблема |
| 190 | Аккаунт |
| 192 | Возврат средств |
| 194 | Расчёты / Финансы |
| 196 | Общий вопрос |
| 198 | Жалоба |
| 200 | Другое |

**Приоритет `UF_CRM_1786685952807`:** 154 — критическая, 156 — важная, 158 — стандартная, 160 — может подождать

**Способ оплаты `UF_CRM_1786686105228`:** 162 — QR, 164 — Cards

> Коды полей и ID значений могут меняться при правках карточки на портале.
> Актуальные значения всегда можно получить вызовами `crm.deal.fields` и
> `crm.contact.fields` (в ответе — `items[].ID` / `items[].VALUE` для списков).

## 6. Ошибки и лимиты

- **Ошибка метода:** ответ содержит `error` и `error_description` (напр.
  `insufficient_scope` — вебхуку не хватает права `crm`).
- **Лимит интенсивности (leaky bucket):** ёмкость 50 запросов, слив 2 запроса/сек
  (на тарифе Enterprise — 250 / 5). При переполнении — `QUERY_LIMIT_EXCEEDED`, HTTP 503.
  Лимит считается **на весь портал**. Рекомендуется ретрай с паузой на 503 и 429.
- **Лимит по времени выполнения:** `OPERATION_TIME_LIMIT`, HTTP 429 — считается на
  вебхук/приложение. Обычными формами практически недостижим.
- **Всплеск запросов → временный бан IP на периметре:** портал может ответить
  «голым» `nginx 403` (HTML, не JSON). Не гонять запросы десятками в секунду;
  бан снимается сам через несколько минут.
- **User-Agent:** всегда задавать непустой — иначе возможен `403` на входе.

## 7. Порядок реализации на стороне бэкенда

1. Принять POST формы, провалидировать (email/телефон, обязательные поля).
2. Собрать источник: домен, URL страницы, `referrer`, `utm_*` (снять на клиенте и передать).
3. Шаг 1 — поиск дубля контакта.
4. Шаг 2/3 — создать контакт (если нужно) и сделку с `CONTACT_ID`.
5. Вернуть форме результат (ID сделки/контакта или текст ошибки).

Референс-реализация на PHP — в `b24-submit.php` этого репозитория; пример формы —
`test-form.html`.
